# Django + DRF Expert

Apply these practices whenever writing or reviewing Django code in this repo, with emphasis on building REST APIs via Django REST Framework (DRF). Prefer Django/DRF's built-in tools over custom code — most "clever" hand-rolled solutions duplicate something the framework already does correctly.

## Package management: uv only

- Use `uv` for every dependency operation — `uv add`, `uv add --dev`, `uv remove`, `uv sync`, `uv lock`. Never hand-edit `pyproject.toml`'s dependency arrays directly or fall back to `pip install`; a `requirements.txt`/`requirements-dev.txt` appearing in the repo is a bug — delete it and migrate its pins into `pyproject.toml` via `uv add`.
- Commit `uv.lock`. Never hand-edit it — it's regenerated by `uv lock`/`uv sync`.
- Runtime deps go in `[project] dependencies`; dev-only tooling (pytest, ruff, mypy, factory_boy, stub packages) goes in the `dev` group under `[dependency-groups]` (`uv add --dev <pkg>`), not mixed into `dependencies`.
- Non-library Django apps aren't installable packages — set `[tool.uv] package = false` in `pyproject.toml` so `uv sync` doesn't try to build/install the project itself, just its dependencies.
- Pin exact versions for framework-critical packages (`django`, `djangorestframework`) the same way the frontend pins `next`/`react` — deliberate upgrades, not silent ones.
- Run `uv run <tool>` (or rely on the image's activated venv on `PATH`) rather than assuming a global install of lint/test tools.

## Project & app structure

- One Django app per bounded domain concept (e.g. `notes`, `accounts`), not one giant `core` app. Keep apps small and focused.
- Split settings into `settings/base.py`, `settings/dev.py`, `settings/prod.py` (or use `django-environ`/`.env`) once there's more than one deployment target. Never commit `SECRET_KEY`, DB credentials, or other secrets — read them from environment variables.
- Keep business logic out of views/viewsets. Put it in model methods, a `services.py`, or manager/queryset methods. Views should orchestrate (validate input, call logic, shape output), not contain the logic itself.
- Use `get_user_model()` / `settings.AUTH_USER_MODEL`, never import the `User` model directly, so a custom user model stays a drop-in swap.

## Models

- Every model needs `__str__`.
- Add `db_index=True` (or `Meta.indexes`) on fields used in frequent filters/lookups (e.g. `owner`, `created_at`).
- Prefer `Meta.ordering` on models that are commonly listed, so API responses are deterministic without every viewset needing `order_by`.
- Use `related_name` deliberately on ForeignKey/OneToOne/ManyToMany so reverse relations read naturally (e.g. `owner = models.ForeignKey(User, related_name="notes", on_delete=models.CASCADE)`).
- Choose `on_delete` intentionally — default to `PROTECT` or `CASCADE` based on real domain semantics, never leave it as an afterthought.
- Push reusable filtering/annotation logic into custom `Manager`/`QuerySet` classes (`Note.objects.published()`, `.owned_by(user)`) instead of repeating `.filter(...)` chains across views.
- Never generate migrations by hand-editing; run `makemigrations` and review the diff before committing. Squash migrations when a app's history gets noisy, but only when asked.

## Serializers

- Prefer `ModelSerializer` over `Serializer` unless the payload doesn't map to one model.
- Keep serializers thin: validation and simple field derivation only. Move cross-field or DB-touching validation into `validate_<field>` / `validate()`, and business rules into the model/service layer, not the serializer.
- Use `read_only_fields` (or explicit `read_only=True`) for server-set fields like `id`, `owner`, `created_at`, `updated_at` — never trust the client to set them.
- Use nested serializers or `SerializerMethodField` for read-heavy relations; use `PrimaryKeyRelatedField` (or slug/hyperlinked variants) for writes. Don't nest-write unless you've implemented `create`/`update` to handle it — DRF doesn't do nested writes for free.
- Set `source=` explicitly when a serializer field name diverges from the model field, rather than renaming the model field to match the API.

## Views & viewsets

- Default to `ModelViewSet` / generic views (`ListCreateAPIView`, etc.) wired through a `DefaultRouter`. Only drop to `APIView` when the endpoint genuinely isn't CRUD-shaped.
- Override `get_queryset()` to scope data to the requesting user/tenant (e.g. `return self.request.user.notes.all()`) — don't rely on `queryset = Model.objects.all()` plus a permission check alone, or you risk leaking existence of other users' objects via 404 vs 403 timing/behavior.
- Override `perform_create()`/`perform_update()` to inject server-controlled fields (`serializer.save(owner=self.request.user)`), never accept them from the request body.
- Use `select_related()` for FK/O2O and `prefetch_related()` for M2M/reverse-FK in `get_queryset()` whenever the serializer touches related objects — this is the #1 source of N+1 queries in DRF APIs. Verify with `django-debug-toolbar` or `assertNumQueries` in tests when in doubt.
- Return correct status codes: 201 on create, 204 on delete-with-no-body, 400 on validation errors (DRF does this by default — don't swallow it with custom try/except that returns 200).

## URLs & routing

- Use `DefaultRouter`/`SimpleRouter` for viewsets instead of manually wiring `path()` per action.
- Version the API from the start if it's public/long-lived (`/api/v1/...`), even if there's only one version today.
- Keep app-level `urls.py` per app, included from the project root `urls.py` — don't centralize every route in one file.

## Authentication & permissions

- Never leave `AllowAny` on endpoints that touch user-owned data. Default `DEFAULT_PERMISSION_CLASSES` to `IsAuthenticated` in settings and open up specific endpoints explicitly, rather than the reverse.
- Use object-level permissions (`IsOwnerOrReadOnly`-style `has_object_permission`) for per-object ownership checks, not just view-level `IsAuthenticated`.
- For token-based auth prefer `djangorestframework-simplejwt` or DRF's `TokenAuthentication` over hand-rolled token schemes. Enable session auth only for the browsable API in dev.
- Enable throttling (`DEFAULT_THROTTLE_CLASSES`/`DEFAULT_THROTTLE_RATES`) on any publicly reachable write or auth endpoint (login, signup, password reset) to blunt brute-force/credential-stuffing.

## Pagination, filtering, ordering

- Set a global `DEFAULT_PAGINATION_CLASS` (e.g. `PageNumberPagination` with a sane `PAGE_SIZE`) — never ship an unpaginated list endpoint over user-generated content.
- Use `django-filter`'s `DjangoFilterBackend` for filtering, `OrderingFilter` for sort, `SearchFilter` for simple text search — don't hand-parse query params in the view.

## Validation & errors

- Let DRF's built-in exception handling produce error responses; only write a custom `exception_handler` if you need a different error shape, and keep it consistent across the whole API.
- Raise `serializers.ValidationError` (not bare `ValueError`/`Exception`) inside serializer validation so DRF formats it correctly.
- Use `get_object_or_404` (or DRF's generic view behavior, which already does this) instead of manual `try/except DoesNotExist`.

## Logging

- Use Python's `logging` module with a per-module named logger (`logger = logging.getLogger(__name__)`) — never `print()` for anything that should survive past local debugging.
- Log meaningful, useful events, not noise: business-relevant occurrences (user signed up, login failed, payment processed, permission denied) at `info`/`warning`, and unexpected failures at `error`/`exception`. Don't log routine successful CRUD operations line-by-line — that's what `django.request`'s access log already covers.
- Pick the level deliberately: `debug` for dev-only diagnostics, `info` for expected business events, `warning` for anticipated-but-notable failures (bad credentials, validation rejected), `error`/`exception` for unexpected failures. Use `logger.exception(...)` (not `logger.error`) inside an `except` block so the stack trace is captured.
- Attach context with `extra={...}` (user id, request id, relevant object id) rather than only interpolating it into the message string, so logs stay filterable/queryable instead of being free-text soup.
- Never log secrets or sensitive PII in the clear — passwords, tokens, full card numbers. Log identifiers (user id/email) instead of the credential itself.
- Configure `LOGGING` explicitly in `settings/base.py` (formatter + console handler at minimum, with per-environment level overrides in `dev.py`/`prod.py`) — don't rely on Django's implicit default, which silently drops most app-level log calls below `WARNING`.

## Performance

- Watch for N+1 queries any time a list serializer touches a related field — fix at the queryset level (`select_related`/`prefetch_related`/`Prefetch`), not by adding caching as a band-aid.
- Use `.only()`/`.defer()` sparingly and only when profiling shows a real win — they're easy to misuse and cause extra queries when a deferred field is accessed later.
- Cache expensive read-heavy, rarely-changing endpoints with DRF's/Django's cache framework rather than pushing that logic into the client.

## Development process: TDD

- Write the test before the implementation, for every model, serializer, view, and permission change: red (failing test) → green (minimal code to pass) → refactor. Don't write production code without a failing test driving it first.
- Keep the red→green loop tight — one behavior per test, run it immediately after writing the implementation, don't batch several untested behaviors before running anything.
- Maintain high coverage as a hard bar, not an afterthought: run `pytest --cov` and treat any drop in coverage on touched files as a signal that a case was skipped, not just a number to note. New code should land with coverage at least as high as the file/app average — untested branches (especially permission checks and validation error paths) are not acceptable.
- Refactor only under green tests. If a refactor needs behavior the tests don't cover yet, add the test first.

## Testing

- Use **pytest** exclusively for all Django/DRF tests — `pytest-django` for the Django integration and the `APIClient`/`api_client` fixture (or `pytest-drf`) for hitting endpoints through HTTP. Do not use Django's `unittest`-style `TestCase`/`APITestCase` classes or `manage.py test`; every new or migrated test should be a plain pytest function/class using `pytest-django` fixtures (`db`, `client`, `settings`, etc.).
- Structure tests as `test_*.py` under each app's `tests/` package, one file per model/serializer/view under test, mirroring the app layout.
- Assert status codes AND response body shape, not just "it didn't 500".
- Use `django_assert_num_queries` (pytest-django) on list endpoints to catch N+1 regressions before they ship.
- Use `factory_boy` with `pytest` fixtures (not Django fixtures/JSON fixtures) for test data, to keep object construction colocated with the tests that need it and avoid duplicating model-construction boilerplate.
- Parametrize with `@pytest.mark.parametrize` for validation/permission edge cases instead of copy-pasting near-identical test methods.
- Enforce coverage in CI: run `pytest --cov=<app> --cov-report=term-missing --cov-fail-under=<threshold>` so a build fails when coverage regresses, not just when tests fail.

## Code quality: type hints, linting, formatting

Apply these on every change, not just at the end of a feature — treat a change as incomplete until it's typed, linted, and formatted.

- **Type hints**: annotate function/method signatures (params and return types) on all new and touched code — model methods, manager/queryset methods, serializer `validate_*`/`validate`, view/viewset methods, service functions. Use `django-stubs` (+ `djangorestframework-stubs`) and run `mypy` so Django/DRF-specific types (querysets, model fields, request objects) are checked, not just plain Python.
- **Linting**: run `ruff check` (or the project's configured linter) before considering a change done; fix findings rather than suppressing them, and only add a `# noqa`/inline ignore with a comment explaining why when the lint is a genuine false positive.
- **Formatting**: run `ruff format` (or `black`) on every touched file so formatting is never part of a diff's review burden or a source of merge noise.
- Wire all three (mypy, ruff check, ruff format --check) plus `pytest --cov` into pre-commit hooks and CI so they run automatically on every change rather than relying on memory to invoke them manually.

## Containerization

- The app is always containerized. There must be a `Dockerfile` for the Django service and a `docker-compose.yml` (or equivalent) wiring it up with its dependencies (Postgres, Redis, etc.) — no "run it locally with a venv" fallback path as the primary workflow.
- **Every command runs inside the container**, never on the host: `docker compose exec web python manage.py <cmd>`, `docker compose exec web pytest --cov`, `docker compose exec web ruff check .`, `docker compose exec web mypy .`. Use `docker compose run --rm web <cmd>` for one-off commands when the service isn't already running.
- Never `pip install`/`uv add` on the host or activate a local venv to run the app/tests/linters — install dependencies inside the image (`docker compose build` after touching `pyproject.toml`/`uv.lock`) and exec into the container for everything else. If a new dependency is needed, run `uv add <pkg>` inside the container (or via `docker compose run --rm backend uv add <pkg>`) so `pyproject.toml`/`uv.lock` update together, then rebuild the image.
- Keep `uv.lock` committed and rebuild the image (`docker compose build`) whenever it changes, rather than installing ad hoc inside a running container and letting the image drift from the lockfile.
- Migrations, management commands, and the dev server all run through `docker compose exec`/`docker compose run` — `docker compose up` should be the one host-level command needed to get the stack running.

## Security checklist

- `DEBUG = False` and a real `ALLOWED_HOSTS` in any non-local settings.
- CSRF stays on for session-authenticated/browser-facing views; only exempt it for genuinely stateless token-authenticated API endpoints, and know why before disabling it.
- CORS: use `django-cors-headers` with an explicit allow-list (`CORS_ALLOWED_ORIGINS`), never `CORS_ALLOW_ALL_ORIGINS = True` in production.
- Never trust client-supplied `owner`/`user`/`is_staff`/`is_admin` fields in request bodies — always set them server-side (see "Views & viewsets" above).
- Run `python manage.py check --deploy` before shipping to catch missed security settings.

## When reviewing existing code

Flag, in priority order: (1) missing per-user queryset scoping / object-level permission checks, (2) unpaginated or N+1-prone list endpoints, (3) client-writable fields that should be server-set, (4) business logic embedded in serializers/views instead of models/services, (5) missing tests around auth/permission boundaries, (6) commands documented/run against a host venv instead of `docker compose exec`/`run`.
